# 实训科管理平台移交校内数据中心对接方案

> **编制单位**：教务处 · 实训管理科
> **编制时间**：2026 年 9 月 10 日
> **事项**：实训科管理平台由教师个人云资源迁移至校内数据中心（校园网），与信息中心对接的沟通安排与技术实施计划

---

## 一、平台现状（对接前须讲清楚的事实）

| 项目 | 现状 |
|------|------|
| 平台名称 | 广西生态工程职业技术学院 · 教务处实训科管理平台 |
| 线上地址 | https://gxstzy-shixun.ai-builders.space |
| 功能模块 | 制度文件、迎检材料、一室一表、实训室分级台账（552 间房间档案）、安全数据驾驶舱、实训科业务、虚拟仿真、获奖入口与竞赛核查 |
| 应用架构 | FastAPI 单进程（约 1300 行 Python）+ 静态页面托管，Docker 镜像已就绪 |
| 身份认证 | Logto Cloud（OIDC），关闭注册、仅邀请，五类角色权限体系（教务处管理员／学院管理员／实验员／教师／学生） |
| 数据库 | Turso（libSQL），节点位于境外（日本东京） |
| 运行环境 | 教师个人账号下的免费云托管（AI Builders Space），空闲自动休眠 |
| 代码管理 | GitHub 私有仓库 |
| 数据规模 | 静态资产约 283 MB（其中制度文档包 260 MB、房间档案 552 页）；数据库为用户与角色表 |

## 二、移交动因（对信息中心与分管领导的官方口径）

按重要性排序，沟通时取前三条即可：

1. **数据安全合规**。平台承载全校实训室分级台账、安全管理信息，静态数据中含约 31 个教职工手机号，数据库用户表含姓名、邮箱、手机号字段。上述数据现存放于境外数据库节点，不符合教育数据与个人信息管理要求，须迁回校内。
2. **业务连续性**。平台目前运行于教师个人账号申请的免费云资源，受额度限制，空闲即休眠（实测健康检查超时），账号变动或服务停运将直接中断科室业务系统。
3. **访问可信度**。现用域名为第三方域名，师生从校园网访问"学校平台"时指向境外第三方地址，存在信任与网络安全层面的瑕疵。
4. **服务稳定性**。免费层冷启动慢，迎检、突击填报等高峰场景不可靠。
5. **资产管理**。自研系统沉淀为学校信息化资产，纳入校内统一管理与备份。

## 三、沟通安排

### 3.1 沟通路径

```
实训科内部定调 → 教务处分管领导同意 → 以教务处名义约信息中心 → 首次对接会 → 联合确认路线 → 分工实施
```

- **第一步（科内）**：明确移交目标为"基础设施校内化 + 数据回校内"，维护主体仍是实训科，不向信息中心转移运维责任。
- **第二步（处内）**：向教务处分管领导汇报，取得处室背书；如信息中心与教务处平级，由处领导出面或发工作联系函效果最好。
- **第三步（跨部门）**：与信息中心开首次对接会，带齐 3.2 节材料，目标只有一个——确认接收路线（第四节的 A／B／C 三选一）和双方责任人。

### 3.2 首次对接会需携带的材料

| 材料 | 内容要点 | 状态 |
|------|----------|------|
| 平台一页纸 | 功能清单、用户群体（五类角色）、访问地址、截图 | 待编制（可从本方案第一节裁剪） |
| 资源申请清单 | 虚拟机规格、域名、证书、网络策略（见 4.2 节） | 本方案已列出 |
| 数据清单与敏感度说明 | 存了什么、在哪里、多少量、含哪些个人信息（见 3.3 节） | 本方案已列出 |
| 运维承诺 | 应用层由实训科维护，故障响应方式，信息中心仅保障基础设施 | 待编制 |
| 技术文档 | 架构图、部署文档（Dockerfile 已备）、健康检查接口 | 仓库已有，需整理 |

### 3.3 数据清单（如实申报）

| 数据 | 位置 | 敏感度 |
|------|------|--------|
| 用户表（姓名、邮箱、手机号、角色、学院） | 境外数据库 | 个人信息，中 |
| 实训室台账（房间档案 552 间、安全等级、责任人及联系电话约 31 个） | 静态资产 | 个人信息＋校园安全管理信息，中 |
| 制度文件包（校内管理文件 260 MB） | 静态资产 | 内部资料，低 |
| 获奖名单、实训室照片 | 静态资产 | 低 |

说明口径：**无身份证号、无密码明文、无学生个人明细**；数据库仅存账号与角色映射。迁移时同步完成数据脱敏复核。

### 3.4 预期问答（会前预案）

| 信息中心可能的问题 | 应答口径 |
|--------------------|----------|
| 谁开发、谁维护？ | 实训科自研自维护，源码完整、文档齐全；信息中心只需提供虚拟机、域名、证书与网络策略，不承担应用运维 |
| 安全怎么保证？ | GitHub 私有仓库可向信息中心开放审计；上线前配合学校网络安全扫描与整改；认证为邀请制，未开放公开注册 |
| 要过等保吗？ | 主动询问流程。若按校内二级等保要求，纳入实施计划，由双方共同推进 |
| 能否对接统一身份认证？ | 现认证为标准 OIDC 协议，改为学校统一身份认证（CAS／OAuth2）技术上成熟，列为二期目标 |
| 校外要访问吗？ | 默认校园网内访问；如迎检期间需校外访问，走学校已有的公网映射或 VPN 通道，由信息中心按校规审批 |

### 3.5 给领导的三十秒版本

> 实训科自建了一套实训室管理平台，零采购成本，已稳定支撑一室一表、迎检、分级台账等业务。目前跑在教师个人的免费云资源上，数据存在境外，不符合要求。申请信息中心支持一台校内虚拟机和校内域名，把数据和系统都搬回校内，应用维护仍由实训科负责，不给信息中心增加运维负担。

## 四、技术实施

### 4.1 三条路线（供信息中心选择，推荐 A）

**路线 A：校内虚拟机 + Docker 部署（推荐）**
- 信息中心提供 1 台虚拟机，实训科用现成 Dockerfile 自行部署；
- 数据库由境外 Turso 改为校内方案：初期直接落地本地 SQLite（libSQL 本就是 SQLite 体系，导出 SQL 即可迁移，工作量以天计），后期视学校规范改接校内 MySQL／PostgreSQL；
- 认证第一阶段保留 Logto（功能不受影响），第二阶段对接学校统一身份认证；
- 对信息中心的要求仅为开机、给域名、放行端口，接收成本最低。

**路线 B：纳入学校容器平台（如学校已有 K8s／容器云）**
- 实训科提交镜像与部署清单，由平台统一调度运维；
- 前提是学校已有容器平台且愿意接收新增业务，对接周期取决于平台管理流程。

**路线 C：数据先行、应用后迁（过渡方案）**
- 若信息中心短期内无法提供资源，先把数据库从境外迁回（校内或境内），应用暂留现网，明确过渡期限并写入会议纪要，待窗口期整体搬迁；
- 该路线不解决域名与休眠问题，仅作退路。

### 4.2 路线 A 资源申请清单（首次对接会直接提交）

| 项目 | 申请内容 | 说明 |
|------|----------|------|
| 虚拟机 | 2 核 CPU／4 GB 内存／40 GB 系统盘 | 应用为单进程轻负载，静态资产 283 MB，配置有余量 |
| 操作系统 | Linux（Ubuntu 22.04 或学校标准镜像） | Docker 部署 |
| 域名 | 校内二级域名（建议形如 shixun.gxstzy.edu.cn） | 由信息中心按校规分配 |
| 证书 | 上述域名的 HTTPS 证书 | 信息中心统一签发 |
| 网络 | 校园网内可访问；服务器出站访问 Logto 认证服务（一期） | 二期对接统一认证后可完全内网闭合 |
| 数据库 | 一期不需要（应用自带 SQLite）；二期如接校内 MySQL／PostgreSQL 再申请 | 降低初期占用 |
| 备份 | 纳入学校统一备份策略（如有） | 数据目录 + 数据库文件每日备份 |

### 4.3 分阶段计划

| 阶段 | 内容 | 周期 | 责任方 |
|------|------|------|--------|
| 0 材料准备 | 一页纸、数据清单、运维承诺定稿；处内汇报定调 | 1 周 | 实训科 |
| 1 首次对接 | 提交材料，确认路线（A／B／C）与双方责任人 | 1–2 周 | 双方 |
| 2 环境落地 | 虚拟机开通、域名证书签发；数据库导出并在校内环境试跑 | 2–4 周 | 信息中心开资源，实训科部署 |
| 3 双轨试运行 | 现网照常服务，校内地址灰度使用，核对数据一致性 | 1–2 周 | 实训科 |
| 4 正式切换 | 校内域名生效，旧服务转只读归档；密钥全量轮换 | 1 周 | 双方 |
| 5 二期收尾 | 对接学校统一身份认证；按学校要求推进等保与安全扫描 | 视校方流程 | 双方 |

关键控制点：**阶段 3 结束前旧平台不得下线**；切换前完成一次全量备份（静态资产 + 数据库）；切换后旧域名保留 30 天跳转提示。

### 4.4 移交物清单（阶段 4 交付信息中心存档）

1. 源码仓库访问权限（GitHub 私有仓 collaborator，或按校方要求迁移至校内代码托管）；
2. Dockerfile 与部署文档（本仓库 README 及《云端部署归档》已有，随迁移更新）；
3. 环境变量清单（仅变量名与用途，密钥值单独线下交接）；
4. 数据库建表脚本与数据迁移脚本；
5. 运维手册：健康检查接口（`GET /health`）、日常巡检、备份与恢复、常见故障处置；
6. 应急联系人表（应用层：实训科；基础设施层：信息中心）。

## 五、风险与红线

| 风险 | 应对 |
|------|------|
| 信息中心人力紧张、接收意愿低 | 全程坚持"自研自维护、只借基础设施"口径，把对方成本压到开一台机器、批一个域名 |
| 流程周期长（等保、安全扫描） | 路线 C 作为兜底，先解决数据出境问题；阶段目标写入会议纪要便于跟踪 |
| 迁移期间数据不一致 | 双轨期以旧库为准，切换日冻结写入、单向同步、核对后切换 |
| 密钥泄露面扩大 | 迁移完成后轮换全部密钥（Logto Secret、数据库凭据、Session Secret）；密钥永远不进 git |
| 个人账号依赖残留 | 逐步将 Logto、域名注册等所有权移交处级主体或信息中心，形成书面记录 |
