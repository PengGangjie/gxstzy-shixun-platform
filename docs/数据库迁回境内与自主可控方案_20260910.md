# 实训科管理平台 · 数据库迁回境内与自主可控执行方案

> **编制单位**：教务处 · 实训管理科
> **编制时间**：2026 年 9 月 10 日
> **前置文档**：《移交校内数据中心对接方案_20260910.md》（路线 A 校内虚拟机为首选；本方案处理其前提不成立时的情形，两者并行不悖）

## 一、数据体量事实（2026-09-10 核查）

| 表 | 行数 | 说明 |
|------|------|------|
| users | 2 | 账号与角色映射 |
| room_photos | 18 | 教室照片，base64 存储，合计约 5.9 MB |
| room_edits / room_equipment | 0 | 尚无写入 |

**结论：全库有效数据不足 10 MB。** 当前不需要任何"数据库服务"，需要的是三样东西：一个境内落点、一套备份纪律、一个可控的登录方案。任何按月付费的云数据库对 10 MB 数据都不构成合理支出。

## 二、国内数据库选型（回答"Turso 换什么"）

| 选项 | 形态 | 费用 | 评价 |
|------|------|------|------|
| **SQLite 本地文件（推荐）** | 应用同机单文件 | 0 | libSQL 本就是 SQLite 体系，SQL 零迁移；数据随应用走，不新增外部依赖与故障面；10 MB 体量性能余量极大 |
| 腾讯云 MySQL（云数据库） | 托管服务 | 约 ¥20–40/月（1C1G 基础版） | 个人实名可购、境内地域；仅当学校规范强制要求"独立数据库服务"时采用 |
| 阿里云 RDS MySQL Serverless | 托管服务 | 按量付费 | 同上 |
| 腾讯云 CloudBase 云开发数据库 | 文档型 NoSQL | 按量，月几元级 | 要把 SQL 改写为文档模型，迁移成本反而最高，不取 |
| PostgreSQL 自托管 | 同机 Docker | 0 | 功能上优于 MySQL，但对当前需求无增益，SQL 方言迁移是净成本，不取 |

**选型结论：SQLite。** 理由：数据量级小、单进程应用、无并发写入压力（当前写入者仅实验员群体）、libSQL→sqlite3 只换驱动不换 SQL。云数据库留给"信息中心将来强制规范化"时再上，届时从 SQLite 导出导入即可，不构成单向门。

## 三、登录方案选型（回答"登录怎么保证安全"）

现用 Logto Cloud 为境外服务（iiyxny.logto.app），境内访问时好时坏，且依赖个人注册的第三方账号。按优先级：

| 优先级 | 方案 | 说明 |
|--------|------|------|
| 1 | **学校统一身份认证** | 单独向信息中心申请"认证接入"而非服务器资源——只要求把平台注册为认证系统的接入应用（CAS／OAuth2），门槛远低于开虚拟机。即使资源申请被拒，这项仍值得单独争取 |
| 2 | **自建邀请制登录（兜底主力）** | 平台用户表本来就自己维护（角色、学院、房间都在自库），Logto 实际只提供"登录 + 邀请"两个动作，自建工作量约 1–2 天（见 6.3 节设计），换回完全可控 |
| 3 | Logto 自托管 | 开源可 Docker 自部署，但需 Node + PostgreSQL，同机资源紧张，配置面大，与自建登录相比无增益，不取 |
| 4 | Authing 等国内 IDaaS | 有免费额度，但引入新的第三方依赖，与"去个人账号依赖"的目标相反，不取 |
| 过渡 | 保留 Logto Cloud | 迁移初期可暂时保留，列入观察项（境内可用性）；自建登录上线后立即切换下线 |

## 四、目标架构（信息中心不提供资源时）

```
师生浏览器
   │ HTTPS（域名备案后）
   ▼
国内轻量云服务器（2C2G，Docker，处室/工作身份注册的云账号）
   ├─ Caddy（反代 + 自动 HTTPS）
   ├─ FastAPI 容器（现有 Dockerfile）
   │    ├─ 认证：自建邀请制登录（或统一身份认证）
   │    └─ 数据：SQLite 单文件（卷挂载，含照片表）
   └─ 备份任务（每日定时）
        ├─ VACUUM INTO 生成一致性快照
        ├─ age 加密
        ├─ 上传腾讯云 COS（境内）
        └─ 同步家庭 NAS（第二落点）
```

要点：
- **云账号以处室或工作身份注册**，把资产名义从个人转向科室，与移交校内是同一逻辑——即使信息中心不出资源，也不再用教师个人账号承载学校业务；
- 服务器选购腾讯云／阿里云轻量应用服务器即可（新用户活动价约 ¥99/年，常态续费约 ¥200–300/年）；
- 境内服务器绑定域名须 ICP 备案（个人可办，免费，约 2–4 周）；备案期间以 IP＋端口试运行，或维持现网双轨。

## 五、安全基线清单

### 5.1 登录面

1. 密码哈希用 bcrypt 或 argon2（passlib），禁明文、禁可逆加密；
2. 会话 Cookie：HttpOnly + Secure + SameSite=Lax，签名密钥为 32 字节以上随机值、每环境独立；
3. 注册仅限邀请码通道（管理员在 `/admin/` 生成），沿用现有"新用户默认 student 最窄角色、永不覆盖人工设定"的 upsert 逻辑；
4. 登录接口限速 + 失败锁定（如 15 分钟内 5 次失败锁 30 分钟）；
5. 找回密码走邮箱一次性 token（10 分钟有效、单次使用）；
6. 全部登录与角色变更写审计日志（时间、账号、动作、IP）。

### 5.2 数据面

1. **备份 3-2-1**：每日快照，COS 与 NAS 双落点，保留 30 天；备份文件加密后才出服务器；
2. **季度恢复演练**：从 COS 取一份备份，在本地空环境完整恢复并核对行数，形成记录——没有演练过的备份不算备份；
3. 手机号等敏感字段应用层加密（Fernet，密钥走环境变量），列为二期加固项；
4. 数据链路自检：应用、数据库、备份、日志四者全部位于境内，无任何出境调用（保留 Logto 过渡期须在切换前移除）；
5. 密钥（数据库口令如设、会话密钥、备份加密密钥）不进 git、不进部署配置，交接时单独线下移交；
6. 所有数据库查询保持参数绑定（现有代码即 `?` 占位风格，SQLite 原生兼容，属验收标准而非额外工作）。

## 六、分步执行计划

### 第 1 周：迁移演练（本地，不动现网）

1. 写导出脚本：libsql-client 遍历读 Turso 全表 → 写入本地 SQLite 文件（保持 `?` 参数绑定）；
2. `app/db.py` 增加 `SQLITE_PATH` 分支：配置了该变量即用 sqlite3 驱动，否则维持 Turso——实现"一套代码、双后端"，迁移和回退都不改业务逻辑；
3. 本地全功能回归：登录、一室一表、房间档案、照片上传、`/admin/` 角色管理、`GET /health`；
4. 验收：两张库行数一致、抽样房间数据一致、照片可显示。

### 第 2 周：境内落点

1. 以处室／工作身份注册云账号，购轻量服务器（2C2G，国内地域）；
2. Docker 部署 FastAPI + SQLite 卷；Caddy 反代；先以 IP＋端口试运行；
3. 提交域名备案（域名 ¥50–80/年，备案免费约 2–4 周）。

### 第 3–4 周：备份与认证

1. 备份脚本上线（每日快照 → age 加密 → COS + NAS），做第一次恢复演练；
2. 启动自建登录开发（或向信息中心递交统一身份认证接入申请，取决于第 2 周沟通结果）：
   - 数据库加 `credentials` 表（用户、密码哈希、邀请状态）；
   - 登录／登出／邀请注册／找回密码四个路由；
   - 替换现有 Logto callback 流程，会话签名机制沿用现有 itsdangerous 实现。

### 备案通过后：切换

1. 域名解析至境内服务器，启用 HTTPS；
2. Turso 做最终增量导出（以切换时刻为准），核对行数；
3. 旧服务转只读，旧域名保留 30 天跳转提示；
4. 轮换全部密钥；注销或降级个人名下的 Turso／Logto 资源。

### 验收标准（汇总）

- 现网功能全部可用，健康检查持续在线（无休眠）；
- 备份可在空环境完整恢复（做过并留记录）；
- 数据库、备份、日志全部位于境内；
- 登录具备第 5.1 节全部六项能力；
- 信息中心若后续同意接收，本架构整体平移进校内虚拟机（Docker 卷拷贝即完成），不推翻重来。

## 八、风险与红线

| 风险 | 应对 |
|------|------|
| 备案周期拖延切换 | 双轨运行：现网照常服务，境内环境就绪即接管；备案非前置依赖 |
| 自建登录引入新漏洞 | 按第 5.1 节清单实现并逐项自查；上线前用学校安全扫描跑一遍 |
| 单机故障（服务器损毁） | 每日双落点备份保证数据不丢（RPO≤24h）；重建时间按 Docker 文档约 1 小时（RTO 可接受） |
| 云账号仍是"人"的 | 处室名义注册 + 密钥交接清单；信息中心将来接收时资产可整体转移 |
| 敏感数据经备份扩散 | 备份加密密钥与云账号凭据分离保管；NAS 上的历史明文备份在加密方案上线后清除 |

## 九、与移交校内方案的关系

两份方案不是二选一：本方案解决"数据立即回境内、登录自主可控"的止血问题，随时可执行、不依赖任何外部审批；移交方案解决"基础设施正式归校"的产权问题，节奏取决于信息中心。执行顺序上，本方案的境内服务器到位后，若信息中心随后同意接收，把 Docker 卷与备份平移进校内虚拟机即可，全部投入不作废。
